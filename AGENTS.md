# Правила разработки проекта

## Specification-first

- Спецификация в `docs/specs/` является source of truth для поведения продукта.
- До изменения поведения сначала обновить соответствующую спецификацию, затем план, задачи, тесты и только после этого production-код.
- Не добавлять поведение, зависимости и точки расширения, которые не требуются утверждённой спецификацией.
- При неоднозначности остановить реализацию и уточнить спецификацию, а не закреплять скрытое предположение в коде.

## Scope и архитектура

- Сохранять минимальный scope и выбирать простейшую структуру, удовлетворяющую спецификации.
- Использовать Python 3.12 или новее и `src`-layout.
- Использовать `uv` и хранить конфигурацию проекта в `pyproject.toml`.
- Для HTTP использовать синхронный `httpx`; не добавлять async или параллельные запросы.
- Не добавлять FastAPI, Flask, Docker, базу данных, DI-framework, сложную DDD/hexagonal архитектуру и другие не требуемые слои.
- Не выполнять рефакторинг и изменения, не относящиеся к текущей спецификации или задаче.

## Тесты и проверки

- Использовать `pytest` для автоматических тестов, `ruff` для lint и format checks, `mypy` для проверки типов.
- Автоматические тесты не должны обращаться к реальному интернету. Подменять HTTP transport, client или границы ввода-вывода детерминированными тестовыми объектами.
- Проверять не только успешный сценарий, но и все ошибки и граничные условия, описанные в спецификации.
- Перед завершением каждого этапа запускать весь актуальный набор проверок: тесты, lint, format check и type check.
- Если какая-либо проверка недоступна или не проходит, явно зафиксировать это в результате этапа.

## Язык и стиль

- README, этот файл, документация в `docs/`, docstrings, содержательные комментарии, CLI help, пользовательский вывод и ожидаемые сообщения об ошибках писать на русском языке.
- Имена функций, классов, переменных, модулей и пакетов писать на английском языке.
- Общепринятые технические термины, например HTTP, URL, CLI, timeout и redirect, можно оставлять на английском языке.
- Commit messages писать на английском языке.
- Не добавлять комментарии и docstrings ради количества. Пустые `__init__.py` оставлять пустыми.

## Рабочий процесс

1. Найти и прочитать применимую спецификацию.
2. При необходимости сначала обновить спецификацию и критерии приёмки.
3. Обновить план и перечень задач.
4. Реализовать минимальное изменение вместе с автоматическими тестами.
5. Обновить русскоязычную пользовательскую документацию, если изменился интерфейс или способ запуска.
6. Запустить все проверки и сопоставить результат с критериями приёмки.
