# Технический план: измеритель скорости загрузки HTTP-ресурса

> Статус: реализация, документация, автоматизация и финальная проверка завершены.

## 1. Цель и границы плана

План реализует поведение из [spec.md](./spec.md) без расширения scope. Приложение остаётся небольшим синхронным CLI: слой CLI управляет вводом, выводом и последовательностью 10 попыток; HTTP-компонент измеряет одну логическую загрузку; компонент расчётов агрегирует результаты. Дополнительные архитектурные слои и абстракции не требуются.

## 3. Ответственность компонентов

### 3.1. CLI и orchestration — `cli.py`

Компонент отвечает за:

- создание `argparse.ArgumentParser` с русскоязычными help-текстами;
- получение и минимальную валидацию единственного позиционного `URL`;
- создание и гарантированное закрытие одного синхронного `httpx.Client` через
  фабрику из HTTP-компонента;
- последовательное потребление 10 результатов измерения из HTTP-компонента;
- немедленный вывод прогресса после каждой успешной попытки;
- передачу 10 результатов в чистую функцию агрегации;
- форматирование итогов до трёх знаков после десятичной точки;
- преобразование ожидаемых ошибок в русскоязычные сообщения и exit codes `0`, `1` или `2` без traceback.

CLI потребляет ленивую последовательность из 10 результатов. Это позволяет выводить
прогресс сразу после каждой попытки без callback, event bus или отдельного
use-case-слоя.

### 3.2. HTTP measurement — `measurement.py`

Компонент выполняет ровно 10 логических GET-запросов через переданный
`httpx.Client` и по одному возвращает результаты попыток. Он отвечает за:

- строго последовательный цикл из 10 попыток;
- начало и окончание измерения через переданную функцию монотонного времени, по умолчанию `time.perf_counter`;
- потоковое чтение конечного ответа через `response.iter_raw()`;
- прямое суммирование длин фактически прочитанных raw chunks;
- полное потребление тела до завершения попытки;
- проверку положительной длительности;
- распознавание конечных статусов 4xx/5xx после чтения тела;
- преобразование ожидаемых HTTP/network/timeout-ошибок в одну небольшую прикладную ошибку измерения с причиной для CLI.

Последовательность результатов реализуется как iterator: следующий запрос начинается
только при запросе следующего результата, после полного завершения предыдущего. Это
сохраняет возможность немедленного progress-вывода в будущем CLI.

Отдельные repository, service, use-case и interface-классы не создаются. Для тестирования достаточно передать настоящий `httpx.Client` с `httpx.MockTransport` и детерминированную функцию времени.

### 3.3. Calculations и data models — `calculation.py`

В одном модуле размещаются две небольшие неизменяемые dataclass-модели и чистая функция расчёта:

- `RequestMeasurement`: `duration_seconds` и `downloaded_bytes` одной успешной попытки;
- `MeasurementSummary`: число запросов, `total_duration_seconds`, `average_duration_seconds`, `total_bytes`, `total_mb`, `speed_mb_s`, `speed_mbps`;
- `calculate_summary()`: проверяет наличие ровно 10 корректных результатов и вычисляет агрегаты без округления.

Модели не содержат HTTP- или CLI-зависимостей. Выделять для них отдельные repository или domain-слои не требуется.

## 4. HTTP strategy

### 4.1. Синхронность и последовательность

Используется только синхронный API `httpx`. Каждый вызов измерения полностью завершается до начала следующей итерации CLI-цикла. Async и concurrency противоречат семантике замера и усложнили бы код без пользы для требований.

Каждый логический запрос использует метод GET без request body. Число логических запросов задаётся внутренней константой `REQUEST_COUNT = 10` и не становится CLI-настройкой.

### 4.2. Один HTTP client

До получения результатов создаётся один `httpx.Client` со следующими параметрами:

- `follow_redirects=True`;
- `max_redirects=20`;
- явный `httpx.Timeout(30.0)`.

Фабрика client размещается в HTTP-компоненте, а управление context manager остаётся в
CLI. Client передаётся в iterator, переиспользуется во всех 10 попытках и закрывается
как при успехе, так и при исключении. Это соответствует спецификации и позволяет
повторно использовать соединения; создание client и его закрытие не входят во время
отдельной попытки.

`follow_redirects=True` рассматривает redirect-цепочку как один логический запрос. HTTPX полностью потребляет промежуточные redirect-ответы перед следующим HTTP-обменом. Время всей цепочки входит в длительность, но байты промежуточных тел не входят в измеряемый объём. Redirect на неподдерживаемую схему, цикл или превышение лимита преобразуется в network error.

### 4.3. Streaming

Конечный ответ открывается через `client.stream("GET", url)`, а его тело читается последовательным обходом `response.iter_raw()`. Streaming предпочтительнее `response.content`, потому что размер ресурса заранее неизвестен: программа не должна удерживать тяжёлый файл целиком в памяти. В памяти остаются только текущий chunk, счётчик bytes и компактные результаты попыток.

Тело читается полностью даже для конечного статуса 4xx/5xx, если транспорт позволяет чтение. Проверка статуса выполняется после чтения. Нельзя безусловно использовать `response.raise_for_status()`, поскольку по спецификации ошибкой являются только 4xx/5xx, тогда как конечный 3xx без следующего redirect не должен автоматически становиться HTTP error.

## 5. Timing strategy

Для каждой попытки `measurement.py` выполняет следующую последовательность:

1. Получает `started_at = timer()` непосредственно перед вызовом `client.stream()`.
2. Открывает логический запрос, следует по redirect и полностью обходит raw chunks конечного body.
3. Сразу после полного чтения получает `finished_at = timer()`.
4. Вычисляет `duration_seconds = finished_at - started_at` без промежуточного округления.
5. При значении `<= 0` завершает замер прикладной ошибкой до вывода успешного прогресса.

Таким образом, длительность включает DNS, подключение, TLS, redirect и чтение конечного тела, но не включает URL validation, создание client, форматирование, печать и вычисление итогов.

В production передаётся `time.perf_counter`. В тестах передаётся простой детерминированный callable с заранее заданными отметками; `sleep` и измерение реального времени не используются.

## 6. Byte counting strategy

Заголовок `Content-Length` нельзя использовать как authoritative value, потому что он может отсутствовать, описывать encoded body или не соответствовать уже фактически прочитанному потоку при сетевой ошибке. Единственный источник значения — chunks, реально полученные при полном обходе потока.

Для каждого raw chunk выполняется:

```text
downloaded_bytes += len(chunk)
```

Используется `iter_raw()`, а не декодирующий `iter_bytes()`, чтобы при HTTP content encoding учитывать переданные encoded bytes до декодирования, как требует спецификация. В подсчёт не входят HTTP headers, framing и тела из `response.history`. Пустое конечное тело даёт 0 bytes.

Если поток завершается исключением или протокольной ошибкой до полного body, попытка считается network error, её частичный объём не включается в результат и следующая попытка не начинается.

## 7. Calculation strategy

`calculate_summary()` получает ровно 10 `RequestMeasurement` и использует исходные `float`/`int` без предварительного округления:

```text
request_count = 10
total_duration_seconds = sum(duration_seconds)
average_duration_seconds = total_duration_seconds / request_count
total_bytes = sum(downloaded_bytes)
total_mb = total_bytes / 1_000_000
speed_mb_s = total_bytes / total_duration_seconds / 1_000_000
speed_mbps = total_bytes * 8 / total_duration_seconds / 1_000_000
```

`total_duration_seconds` хранится в итоговой модели и служит знаменателем обеих скоростей, но не добавляется в пользовательский вывод, поскольку спецификация этого не требует. Итоговая скорость не вычисляется как среднее индивидуальных скоростей.

Округление до трёх знаков применяется только в `cli.py` через форматирование вывода. `total_bytes` выводится целым числом; нулевой общий объём допустим и даёт нулевые скорости при положительном общем времени.

## 8. URL validation

CLI выполняет минимальную локальную проверку до создания сетевого запроса:

1. `urllib.parse.urlsplit()` разбирает значение; ошибки разбора перехватываются.
2. Схема сравнивается без учёта регистра и должна быть ровно `http` или `https`.
3. Проверяется непустой `hostname`; доступ к `port` дополнительно выявляет некорректный номер порта.
4. Fragment удаляется при сборке URL перед передачей в HTTP-компонент, поскольку он не отправляется серверу.

Не выполняются DNS lookup, probing ресурса, allowlist хостов или иная сетевая «валидация». Ошибка входного URL оформляется средствами `argparse`, не вызывает HTTP transport и завершается кодом 2. Стандартные `-h` и `--help` завершаются кодом 0 без сетевых вызовов.

## 9. Error strategy

Ошибки обрабатываются fail-fast: после первой ошибки цикл прекращается, retries отсутствуют, итоговый успешный блок не печатается. Уже напечатанный прогресс предыдущих попыток остаётся в `stdout`. Ожидаемые ошибки выводятся в `stderr` без traceback.

| Ситуация | Место обработки | Поведение | Exit code |
|---|---|---|---:|
| Отсутствующий/лишний аргумент, invalid URL | `argparse` / URL validator | Русскоязычная usage/error-подсказка, HTTP не вызывается | 2 |
| Конечный HTTP status 4xx/5xx | После полного чтения final body | Сообщение с номером попытки и status code | 1 |
| `httpx.TimeoutException` | HTTP measurement | Сообщение с номером попытки и timeout | 1 |
| Иные `httpx.RequestError` | HTTP measurement | Краткая безопасная причина, включая connection/TLS/redirect/protocol errors | 1 |
| Длительность `<= 0` | HTTP measurement | Ошибка измерения до progress и следующей попытки | 1 |

Фиксированный `httpx.Timeout(30.0)` задаёт 30-секундный timeout для connect/read/write/pool операций; для последовательных GET без тела запроса фактически значимы прежде всего connect и read timeout. Значение не доступно через CLI.

Номер попытки добавляет orchestration-код CLI, поскольку HTTP-компонент намеренно измеряет одну попытку и не знает её позиции в серии.

## 10. CLI и output

Публичная команда:

```text
internet-speed-meter URL
```

Ожидаемый успешный вывод в `stdout` имеет стабильные русскоязычные labels и следующую форму:

```text
Запрос 1/10: 0.123 с, 1234567 байт
...
Запрос 10/10: 0.120 с, 1234567 байт

Итоги:
Запросов: 10
Среднее время запроса: 0.121 с
Скачано: 12345670 байт (12.346 MB)
Средняя скорость: 10.203 MB/s (81.624 Mbps)
```

Числа в примере иллюстративны. Для каждой попытки progress печатается только после полного body, проверки положительной длительности и проверки HTTP status. Итоговый блок печатается только после 10 успешных строк progress.

Ожидаемые классы сообщений в `stderr`:

- invalid URL: требуется один абсолютный HTTP/HTTPS URL;
- HTTP error: номер попытки и status code;
- timeout: номер попытки и превышение времени ожидания;
- network/request error: номер попытки и краткая причина;
- ошибка времени: номер попытки и невозможность получить корректную длительность.

## 11. Testing strategy

Все тесты детерминированы, не используют реальный интернет и не вызывают `sleep`.

### 11.1. Расчёты

`test_calculation.py` проверяет:

- сумму длительностей, среднее время, total bytes и десятичные MB;
- формулы MB/s и Mbps;
- отличие агрегированной скорости от среднего индивидуальных скоростей;
- нулевой объём при положительном времени;
- отказ для количества результатов, отличного от 10, и для некорректных данных.

### 11.2. HTTP measurement

`test_measurement.py` использует один настоящий `httpx.Client` с
`httpx.MockTransport` и управляемые реализации `httpx.SyncByteStream`. Тесты
проверяют:

- ровно 10 последовательных GET через один client;
- чтение многочастного final body до конца и подсчёт raw bytes без `Content-Length`;
- encoded body: подсчёт raw, а не decoded bytes;
- пустое тело;
- redirect-цепочку, полное чтение промежуточных тел и исключение их bytes из результата;
- лимит/cycle и redirect на неподдерживаемую схему;
- HTTP 4xx/5xx только после полного чтения body;
- timeout, connection error и преждевременный разрыв потока;
- границы вызовов подменённого таймера и отказ при длительности `<= 0`.

Управляемый stream фиксирует события чтения, чтобы доказать, что следующий HTTP-обмен не начинается до полного потребления предыдущего body.

### 11.3. CLI

`test_cli.py` вызывает `main()` с контролируемыми аргументами и перехваченными
`stdout`/`stderr`. CLI импортирует небольшую функцию `create_client()` из
`measurement.py`; тест подменяет импортированную в CLI ссылку и возвращает настоящий
client с `MockTransport`, не вводя отдельный interface-класс. Проверяются:

- отсутствие, избыток и валидность аргументов, `-h`/`--help`;
- схемы HTTP/HTTPS без учёта регистра и отклонение остальных схем;
- ровно 10 последовательных GET без body через один client;
- немедленный progress `1/10` … `10/10` и формат итогов;
- закрытие client при успехе и всех ошибках;
- fail-fast, отсутствие итогов и exit codes для каждой категории ошибок;
- отсутствие traceback в ожидаемых пользовательских ошибках.

Тесты форматирования сравнивают labels и значения после округления, а тесты расчётов сравнивают неокруглённые значения отдельно.

## 12. Development interface и CI

Небольшой `Makefile` предоставляет targets `help`, `install`, `format`,
`format-check`, `lint`, `typecheck`, `test`, `check` и `run`. Он не содержит
бизнес-логики и вызывает те же команды `uv`, которые можно запустить напрямую.
Target `run` требует явно передать `URL`.

Минимальный GitHub Actions workflow содержит один job для Ubuntu и Python 3.12:

1. checkout репозитория;
2. установка `uv` официальным action;
3. установка Python 3.12 через `uv`;
4. `uv sync --locked --dev`;
5. `uv run ruff format --check .`;
6. `uv run ruff check .`;
7. `uv run mypy src`;
8. `uv run pytest`.

Локальная инструкция в README показывает как Makefile targets, так и прямые
`uv`-команды. Matrix по ОС и версиям Python, публикация package, coverage gate и
deployment не добавляются, поскольку не нужны текущей спецификации.

## 13. Non-goals

Не реализуются:

- async и concurrency;
- retries и продолжение серии после ошибки;
- настройка числа запросов, timeout или redirect limit через CLI;
- database и хранение истории;
- Docker;
- web API, FastAPI и Flask;
- upload/latency/jitter/packet-loss tests;
- benchmarking UI, GUI и графики;
- выбор тестового сервера и попытка заменить ISP speed test;
- сложная plugin architecture;
- repository/service/use-case/interface abstractions, DI-framework и DDD/hexagonal layers;
- подсчёт headers, protocol framing, TLS/TCP overhead и тел промежуточных redirect-ответов.
